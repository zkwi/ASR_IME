# ASR 质量与延迟守门清单

本文记录当前实测有效的 ASR 速度/效果组合。后续改 ASR、OCR、停录尾音或字幕链路时，先读本页，再决定是否需要改参数或代码。

## 已验证有效的组合

- 默认 ASR 音频分片保持 `200ms`，实际发送仍限制在豆包建议的 `100-200ms` 范围内。
- 速度优化主要来自本地链路：首字加速、`20ms` WebSocket 响应轮询、`50ms` 字幕节流、`500ms` OCR 上下文等待上限。
- 停录尾音默认至少收约 `250ms`，仍检测到人声时最多约 `400ms`；真实尾音被切断时优先调大这个窗口。
- 最终输出必须等待豆包最终包。实时字幕、中间包和未带最终包的 `definite=true` 分句只作反馈或内部候选。
- 最终包文本提取优先使用 `result.text`，实时字幕才可以为了跟手感优先展示更完整的 `utterances` 拼接文本。
- `definite=true` 分句用于稳定最终文本，但不能压掉更完整且高度重合的最终包整段文本；最终包补齐开头或尾字时应保留最终包，即使最终包对前文有轻微缩写。
- `enable_ddc=false` 默认更适合识别效果优先，尤其是专有词、短命令、代码标识符和标点敏感口述；已有用户配置显式开启时保留用户选择。
- 屏幕 OCR 上下文默认等待 `500ms`，超时只跳过上下文，不阻断录音、ASR 最终结果、LLM 润色或粘贴。

## 不应回退的做法

- 不要为了让字幕更快，把默认 `200ms` ASR 分片改得更短。更短分片会改变服务端处理节奏，收益不稳定。
- 不要把中间识别文本作为最终文本兜底。缺少最终包时应失败，而不是粘贴可能缺头缺尾的文本。
- 不要为了尾字问题直接加尾部静音包。当前策略是收真实尾音、flush 不足一片的 PCM，并把最后一个真实音频包作为负包发送。
- 不要默认开启 DDC 来追求长句顺滑。顺滑属于文风优化，容易和“原样识别准确”冲突。
- 不要把 OCR 文本、识别正文、热词、prompt 或最近上下文写入日志、统计、诊断报告或发布审计。

## 改动前评估

修改 ASR 相关链路前，先回答：

1. 这是识别效果问题、字幕起步慢、最终粘贴慢，还是用户体感混合问题？
2. 问题发生在采集、OCR 等待、ASR 建连、发包节奏、最终包等待、LLM 润色还是剪贴板输出？
3. 是否有日志或测试证明是代码 bug，而不是配置取舍？
4. 是否会改变最终包门禁、`definite=true` 分句选择、尾音窗口、音频分片或 OCR 等待？
5. 是否需要同步 README、英文 README、Wiki、`docs/audits/2026-06-06-audio-fragment-delivery-audit.md` 和本页？

## 手工回归

- 说完最后一个字立刻停止，确认尾字保留。
- 按开始后立刻说短句，确认开头两个字保留。
- 连续长句输入，确认最终粘贴不是中间字幕。
- 屏幕中有相关术语时，确认 OCR 上下文能帮助专有名词；OCR 超时仍能正常完成识别。
- 开启/关闭 LLM 润色各试一次，区分 ASR 识别速度和最终粘贴速度。

## 允许调整的信号

- 如果 final 包正确但最终输出丢尾字，优先检查 `select_final_output_text` 和相关 `final_output_` 回归测试。
- 如果 final 包的 `result.text` 已补尾字但输出仍缺尾字，优先检查最终包是否误用了实时字幕提取逻辑。
- 如果 final 包本身缺尾字，优先调大 `stop_grace_ms` 或尾音窗口，并验证 flush/负包链路。
- 如果字幕起步慢但最终效果好，优先检查 OCR 等待、WebSocket 建连和首字加速，不优先改 ASR 分片。
- 如果最终粘贴慢但字幕正常，优先检查 LLM 润色耗时和 `min_chars`，不要误改 ASR 采集链路。
